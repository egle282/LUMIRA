# ТЗ: Финальная техническая приёмка LUMIRA

**Версия:** 1.0  
**Приоритет:** P0 — критический  
**Исполнитель:** AI-агент в Antigravity IDE (Gemini)  
**Тип работ:** технический аудит, тестирование, устранение дефектов, повторная приёмка  
**Режим Git:** только локальная работа, без `push`  
**Критерий завершения:** подтверждённая техническая готовность продукта либо исчерпывающий отчёт о блокирующих проблемах.

## 1. Цель

Провести независимую финальную техническую приёмку проекта LUMIRA.

Необходимо установить фактическое состояние приложения, проверить его ключевые пользовательские сценарии, безопасность, инфраструктуру, качество кода, корректность конфигурации и соответствие заявленным требованиям.

По результатам необходимо:

1. Подтвердить или опровергнуть готовность LUMIRA.
2. Выявить критические, высокие, средние и низкие дефекты.
3. Исправить безопасно устранимые дефекты.
4. Повторно выполнить все затронутые проверки.
5. Подготовить доказательный итоговый отчёт.
6. Сформировать конкретный перечень оставшихся работ, если выпуск пока невозможен.

**Запрещено подменять фактическую проверку предположениями, результатами предыдущих запусков или текстом существующих отчётов.**

## 3. Обязательные ограничения

### 3.1. Git и сохранность данных

1. Не выполнять `git push`, `git push --force` и публикацию изменений.
2. Не выполнять `git reset --hard`.
3. Не выполнять `git clean -fd`, `git clean -fdx`.
4. Не удалять Docker volumes и постоянные данные.
5. Не выполнять команды, уничтожающие базы данных, пользовательские данные или окружение.
6. Не перезаписывать `.env`, `.env.local` и другие файлы с секретами.
7. Не менять историю коммитов.
8. Не переключать ветки без необходимости и согласования.
9. Не включать секреты, токены, пароли, приватные ключи и персональные данные в отчёты.
10. Не создавать коммиты без отдельного разрешения пользователя.
11. Не изменять другие проекты и контейнеры Docker на компьютере.
12. Перед любыми потенциально разрушающими действиями остановиться и запросить разрешение.

До начала проверок зафиксируй:

- текущую ветку;
- `HEAD`;
- `origin/main`;
- результат `git status`;
- наличие локальных незакоммиченных изменений;
- список локальных коммитов, отсутствующих в `origin/main`.

Если появились незакоммиченные изменения, которых не было в исходном состоянии, не перезаписывай их и не включай в свои исправления без необходимости.

### 3.2. Секреты и внешние сервисы

Не выводи секреты в терминал без необходимости и не копируй значения секретов в отчёт.

Не отправляй реальные сообщения пользователям, не инициируй платёжные операции, не выполняй реальные списания, рассылки и действия в производственных аккаунтах.

Используй тестовые учётные записи, тестовую инфраструктуру и mock-объекты там, где это необходимо.

Не обращайся к платным внешним API без согласованного бюджета и разрешения.

Не запускай миграции с разрушительными последствиями.

### 3.3. Правила исправлений

Разрешено самостоятельно исправлять локально:

- воспроизводимые ошибки;
- дефекты тестов;
- проблемы конфигурации;
- ошибки API и frontend;
- нарушения изоляции данных;
- недостатки валидации;
- проблемы обработки ошибок;
- небезопасное логирование;
- документированные несоответствия требованиям.

Перед существенными архитектурными изменениями, заменой библиотек, перестройкой схемы БД или изменением публичных API оцени риски.

Если исправление требует изменения архитектуры, миграции данных, платных ресурсов или необратимых операций, сначала подготовь план и запроси согласование.

Не отключай тесты, проверки безопасности или ограничения ради получения зелёного результата.

### 7.1. Изоляция tenants и RLS

Проведи тестирование как минимум с двумя независимыми тестовыми tenants:

- Tenant A;
- Tenant B.

Создай отдельные тестовые учётные записи и тестовые данные.

Проверь, что пользователь Tenant A:

- видит только разрешённые ему данные;
- не может читать данные Tenant B;
- не может изменять или удалять данные Tenant B;
- не может получить чужие данные подменой ID в URL, параметрах или теле запроса;
- не может обходить ограничения через альтернативные API-маршруты.

Проверь аналогичные сценарии для Tenant B.

Если используется PostgreSQL RLS, проверь:

- фактическое наличие и состояние политик;
- включение RLS на необходимых таблицах;
- поведение запросов от имени прикладной роли;
- контекст tenant в транзакциях и соединениях;
- повторное использование соединений из пула;
- отсутствие утечки tenant-контекста между запросами;
- невозможность обхода RLS привилегированной ролью приложения.

Не проводи тесты только от имени суперпользователя PostgreSQL: он может обходить RLS и создавать ложноположительный результат.

Не отключай RLS для прохождения тестов.

**Критерий:** отсутствие подтверждённых межтенантных утечек и несанкционированного доступа. Любая воспроизводимая утечка — блокирующий дефект.

## 13. Этап 10. Устранение дефектов

Для каждого обнаруженного дефекта укажи:

- уникальный ID;
- уровень критичности;
- компонент;
- шаги воспроизведения;
- фактическое поведение;
- ожидаемое поведение;
- техническую причину;
- предлагаемое исправление.

Приоритеты:

- **P0 — Critical:** компрометация данных, обход авторизации, межтенантная утечка, разрушение данных, критическая уязвимость.
- **P1 — High:** невозможность запуска, регистрации, авторизации или выполнения основной бизнес-функции; серьёзная ошибка целостности.
- **P2 — Medium:** существенная, но обходная функциональная ошибка.
- **P3 — Low:** косметические дефекты и незначительные улучшения.

Порядок работы:

1. Сначала воспроизведи дефект.
2. Определи первопричину.
3. Внеси минимальное безопасное исправление.
4. Проведи тест, подтверждающий исправление.
5. Повтори связанные регрессионные тесты.
6. Зафиксируй изменённые файлы и результаты.

Не пытайся исправить всё путём массового рефакторинга.

Если исправление не удалось, сохрани доказательства и опиши остаточный риск. Не заявляй о закрытии дефекта без повторной проверки.

Не создавай Git-коммиты без отдельного разрешения.

- production-сборка frontend;
- тесты авторизации;
- тесты изоляции tenants;
- проверка Git и секретов;
- `git diff --check`;
- проверка итогового состояния рабочего дерева.

Сравни результаты до и после исправлений.

Если какие-либо проверки не выполнены, укажи точную причину. Не заменяй их утверждением «ошибок не обнаружено».

## 16. Формат итогового результата

В финальном сообщении выдай краткую сводку:

**Статус приёмки:** один из вариантов:

- `PASS` — все обязательные проверки пройдены, критических дефектов нет.
- `PASS WITH LIMITATIONS` — основные проверки пройдены, но есть документированные ограничения, не позволяющие подтвердить полную готовность.
- `FAIL` — есть блокирующие дефекты или не выполнены обязательные проверки.
- `BLOCKED` — проверки невозможно завершить из-за внешних ограничений, отсутствующих разрешений или недоступной инфраструктуры.

Затем укажи:

- проверенный commit SHA;
- какие проверки реально выполнены;
- сколько тестов пройдено, провалено и пропущено;
- найденные P0/P1/P2/P3;
- какие дефекты исправлены;
- какие исправления подтверждены повторными тестами;
- какие проверки не удалось выполнить;
- пути к трём итоговым документам;
- изменённые файлы;
- состояние Git;
- подтверждение отсутствия `push`;
- оставшиеся блокеры.

Не объявляй продукт готовым, если ключевые проверки пропущены.

## 17. Критерии завершения задачи

Задача считается завершённой, когда:

1. Проведена инвентаризация проекта.
2. Фактическое состояние приложения проверено.
3. Критические пользовательские сценарии протестированы.
4. Проверены авторизация и изоляция tenants.
5. Выполнены доступные тесты и сборки.
6. Выявленные безопасно устранимые дефекты исправлены.
7. Исправления подтверждены повторными проверками.
8. Итоговые документы созданы и проверены на секреты.
9. Указаны все непроверенные области и остаточные риски.
10. Итоговый вердикт основан на фактических результатах.
11. Не выполнен `git push`.
12. Не удалены постоянные данные и Docker volumes.
13. Не изменены другие проекты и несанкционированные настройки.

Если продукт не прошёл приёмку, задача всё равно должна завершиться полноценным отчётом с конкретными блокерами, доказательствами и последовательностью дальнейших исправлений.

**Главный принцип:** результатом является не сообщение «всё готово», а воспроизводимое доказательство того, что LUMIRA работает, либо точное описание того, что мешает признать продукт готовым.
